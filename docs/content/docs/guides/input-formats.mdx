The worker accepts every file type MinerU 4 reads, through the same three sources (`file_url`, `file_b64`, `volume_path`). The type is **detected by MinerU from the input bytes** — there's no `format` field to set, and the field name `file_*` is intentionally format-agnostic. Send whichever source you have; MinerU detects the type.

## Supported formats

| Format | How it is read |
|---|---|
| **PDF** | With the `tier`, `ocr_mode` and `image_analysis` of the job. The only type that takes a page window (`start_page` / `end_page`) |
| **Image** (PNG / JPEG / GIF / BMP / TIFF / WebP) | As a one-page PDF, with the same settings. MinerU makes the page itself; the worker passes the file as it is. DocVortex 0.5.16 opens the image once and makes one page of it, so the later frames of a multi-frame TIFF or GIF are, by reading its source, not read (not run against a real file): send multi-page scans as a PDF |
| **Office** (DOC / DOCX / PPT / PPTX / XLS / XLSX), **OpenDocument** (ODT / ODS / ODP), **RTF**, **EPUB**, **OFD**, **HTML / MHTML**, **CSV / TSV** | As whole documents, without models, in tier `flash`. The job's `tier`, `ocr_mode` and `image_analysis` have no effect on them, and the response says `tier: "flash"` |

MinerU decides the type from the content: from the file's signature and container structure, and for text such as HTML from its content classifier — a job carries no file name (`basename` has no extension). Whether that holds for a given HTML file is something to check on your own material.

Plain text, Markdown and other text formats are not parsed; the job fails with the type MinerU detected.

## What gets returned

MinerU 4's own files, plus a full-mode Markdown, whatever the input format: `markdown.md`, `markdown_full.md`, `middle_json.json`, `structured_content.json`, `model_output.json` (when MinerU has raw output) and `images/`. See [API reference → What a job's files are](/reference/api/#when-transport-inline). The exact contents differ by format, but the layout doesn't.

## How a PDF or image is read

Three settings, per job:

| Setting | Values | Default |
|---|---|---|
| `tier` | `flash`, `basic`, `standard`, `advanced` | `advanced` |
| `ocr_mode` | `ocr`, `txt`, `auto` | `ocr` |
| `image_analysis` | `true`, `false` | `true` (acts only in `advanced`) |

`ocr_mode` decides where the text of a page comes from. In `ocr` the model reads it. In `txt` it comes from the PDF's own text layer, which is exact on a clean digital PDF and presumably faster, and which is also the damage on a damaged one: in text mode the model does not read running text, titles, headers, footers, page numbers or page footnotes itself. That is why `ocr` is the default. `auto` lets MinerU choose per file, and the response says what it chose.

The language needs no setting: MinerU 4 recognises it itself. The `lang` field of MinerU 3.4 was removed.

## Examples

### PDF

```json
{
  "input": {
    "file_url": "https://example.com/report.pdf"
  }
}
```

Read in tier `advanced` with forced OCR and image analysis.

### A clean digital PDF, text layer

```json
{
  "input": {
    "file_url": "https://example.com/report.pdf",
    "ocr_mode": "txt"
  }
}
```

### Scanned image (PNG)

```json
{
  "input": {
    "file_url": "https://example.com/page-scan.png"
  }
}
```

The image goes to MinerU as the file it is.

### DOCX

```json
{
  "input": {
    "file_url": "https://example.com/spec.docx"
  }
}
```

Read as a whole document in tier `flash`; the response reports `"tier": "flash"`.

## Size limits

| Source | Max input size |
|---|---|
| `file_b64` (inline) | Whole JSON request: 20 MB on `/runsync`, 10 MB on `/run`. Because base64 expands the file, keep raw input below roughly 15 MB or 7.5 MB respectively. |
| `file_url` | 200 MB (worker download cap); fetched with a 120 s timeout |
| `volume_path` | No hard cap; only limited by the network volume's free space |

The worker also rejects decoded `file_b64` data over 20 MB, but the gateway's
whole-request limit normally triggers first. For files up to 200 MB, use a
short-lived signed object URL via `file_url`. For larger books or archives,
pre-stage on a network volume and use `volume_path` — see
[Network volumes](/guides/network-volumes/).

## Page selection (PDF only)

`start_page` / `end_page` apply to PDFs. The worker hands the window to MinerU as its 1-based `page_range`; for any other file type MinerU 4 rejects a page range and the job fails. A job without a window, the whole document, sends none.

## When the type is not what you meant

The worker no longer checks magic numbers itself: MinerU decides. A file MinerU does not recognise or does not read fails the job with the type it detected.

One consequence deserves attention, because MinerU 4 reads HTML: a `file_url` that returns an **HTML error page** (a 403 from an object store with expired credentials, say) is no longer rejected as "unknown bytes". It should be parsed as an HTML document, and the job should succeed with the error page's text (not yet confirmed on a recorded HTML file). If `file_url` can fail that way, look at what came back (the first lines of `markdown` show it) before trusting the job.

This page documents the JSON payload contract the worker accepts. It mirrors the docstring in [`handler.py`](https://github.com/sergeyshmakov/mineru-runpod/blob/main/handler.py), which is the source of truth; this is a friendlier rendering.

## Job input

Send a POST to `/v2/{endpoint_id}/runsync` (or `/run` for async) with an `input` object:

```json
{
  "input": {
    "file_url":       "https://example.com/report.pdf",
    "start_page":     0,
    "end_page":       99,
    "tier":           "advanced",
    "ocr_mode":       "ocr",
    "image_analysis": true,
    "transport":      "tarball_b64",
    "formats":        ["markdown", "markdown_full", "middle_json", "structured_content", "model_output", "images"],
    "basename":       "my-doc"
  }
}
```

Complete cURL request:

```sh
curl --request POST "https://api.runpod.ai/v2/<endpoint-id>/runsync" \
  --header "Authorization: Bearer $RUNPOD_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"input":{"file_url":"https://example.com/report.pdf","transport":"inline","formats":["markdown"]}}'
```

### Required (exactly one of)

The worker accepts every file type MinerU 4 reads, detected by MinerU from the bytes (a job carries no file name): PDF and images (PNG, JPEG, GIF, BMP, TIFF, WebP, JP2), and as whole documents Office (DOC, DOCX, PPT, PPTX, XLS, XLSX), OpenDocument (ODT, ODS, ODP), RTF, EPUB, OFD and HTML/MHTML. CSV and TSV are not accepted: without a file name MinerU detects delimited text as plain text, which it does not read. A file MinerU does not recognise fails the job with the type it detected (or says it found none), and one it recognises but cannot read fails it with MinerU's own reason; either way the response's `error` carries it. **Provide exactly one input source; providing zero or two raises a validation error.**

| Field | Type | Notes |
|---|---|---|
| `file_url` | string | HTTP/HTTPS URL the worker can `GET`, resolving to a publicly routable host. Downloaded server-side with a 200 MB cap and a 120 s timeout. See [`MINERU_ALLOW_LOCAL_FETCH`](#url-inputs) for serving documents from inside your own network |
| `file_b64` | string | Base64-encoded file bytes. RunPod caps the whole JSON request at 10 MB on `/run` and 20 MB on `/runsync`. Base64 adds about 33%, so keep raw files below roughly 7.5 MB and 15 MB respectively; for larger inputs use `file_url` or `volume_path`. |
| `volume_path` | string | Absolute path to a file inside the container, under one of the worker's [input roots](/guides/network-volumes/#what-volume_path-accepts). Useful for files mounted via a RunPod network volume or baked into the image |

### Optional

| Field | Type | Default | Notes |
|---|---|---|---|
| `start_page` | int | `0` | 0-based, inclusive. Only PDFs take a page window. MinerU 4 rejects one for any other file type, an image included, so for those the worker sends none and the file is read whole |
| `end_page` | int | `-1` | 0-based, inclusive. Any negative value or omission means "to end of document". When set, must be `>= start_page`. The worker hands the window to MinerU as its 1-based `page_range` |
| `tier` | string | `"advanced"` | How deeply MinerU reads a PDF or image: `flash`, `basic`, `standard` or `advanced`. Files that are not PDFs or images are always read whole, without models, in `flash`, and the response says so. See [Choosing a GPU → Picking a tier](/guides/choosing-gpu/#picking-a-tier) |
| `ocr_mode` | string | `"ocr"` | Where the text of a page comes from: `ocr` (the model reads it), `txt` (the PDF's own text layer, exact on clean digital PDFs and presumably faster) or `auto` (MinerU chooses per file). `ocr` is the default because the text layer of a damaged PDF is the damage: in text mode the model does not read running text, titles, headers, footers, page numbers or page footnotes itself |
| `image_analysis` | bool | `true` | Let the model describe pictures and charts; the descriptions land in the Markdown behind the image. Acts only in tier `advanced` and is reported as off elsewhere |
| `transport` | string | `"tarball_b64"` | How the worker ships output. `"tarball_b64"` (default, base64-encoded .tar.gz inside the entry), `"inline"` (per-format keys inside the entry, filterable via `formats`), or `"s3"` (presigned URL — requires `BUCKET_*` env vars on the endpoint). See [Output modes](/guides/output-modes/). |
| `formats` | array of string | all six | Subset of `["markdown", "markdown_full", "middle_json", "structured_content", "model_output", "images"]`. Selects which artifacts the inline payload contains. Omit (or pass all six) to get everything. **No-op for `tarball_b64` and `s3`** — those transports always ship a self-contained archive with every file. Empty list is rejected. |
| `basename` | string | `"doc"` | Label echoed in the response entry, handy for correlating many jobs. MinerU 4 names its own output files, so it names none. Must be alphanumeric with `-` or `_`, at most 128 characters |
| `archive_format` | string | `"tar.gz"` | Archive container for the `tarball_b64` and `s3` transports: `"tar.gz"` (default) or `"zip"`. No-op for `inline`. See [Output modes → archive format](/guides/output-modes/#archive-format-targz-or-zip). |
| `probe` | bool | `false` | Diagnostic mode. `{"probe": true}` skips parsing and every field above, then returns the worker's filesystem layout plus the running MinerU version instead of a parse result — for checking baked model paths and volume mounts. On by default; set `MINERU_DISABLE_PROBE=1` on the endpoint to turn it off, where callers should not see filesystem paths or model-cache details. Any value other than `0`/`false`/`no`/`off` disables it, so a typo denies rather than exposes. |

### Fields MinerU 4 removed

A job that sends one of these is rejected, and the error says what takes its place. They belonged to MinerU 3.4's backends, which MinerU 4 no longer has.

| Removed | Takes its place |
|---|---|
| `backend` | `tier` and `ocr_mode`. The old `vlm-*` and `hybrid-*` backends correspond to `tier: "advanced"`, the old `pipeline` backend to `tier: "basic"` |
| `effort` | `image_analysis`. The old `effort: "high"` is `image_analysis: true`, which acts in tier `advanced` |
| `lang` | nothing — MinerU 4 recognises the language itself |
| `formula_enable`, `table_enable` | nothing — MinerU 4 has no such switch |
| `server_url` | nothing — it belonged to the `*-http-client` backends; MinerU 4 reads inside the worker. `MINERU_ENFORCE_TARGET_POLICY` and `MINERU_ALLOWED_SERVER_HOSTS` went with it |

### URL inputs

`file_url` is checked before the worker acts on it:

- It must be `http://` or `https://` with a host. Anything else is rejected with the field name in the message.
- It must additionally resolve to a publicly routable address — what a document URL handed to a serverless worker normally is. Set `MINERU_ALLOW_LOCAL_FETCH=1` on the endpoint when you serve documents from a host inside your own network, or when running the handler locally against `http://localhost`.

## I just want the Markdown — how do I get it?

Set `"transport": "inline"` and (optionally) filter to just markdown:

```json
{
  "input": {
    "file_url": "https://example.com/report.pdf",
    "transport": "inline",
    "formats": ["markdown"]
  }
}
```

Response (truncated):

```json
{
  "ok": true,
  "elapsed_seconds": 4.2,
  "mineru_version": "4.0.12",
  "tier": "advanced",
  "ocr_mode": "ocr",
  "image_analysis": true,
  "results": [
    {
      "basename": "doc",
      "source": "url:https://example.com/report.pdf",
      "pages_requested": -1,
      "markdown": "# Document title\n\nFirst paragraph...\n\n## Section\n\nA table:\n\n<table>...</table>\n"
    }
  ],
  "debug": {"...": "..."}
}
```

For single-file jobs the markdown lives at `result.results[0].markdown`. Higher-level helpers: the Python `MineruClient` exposes `MineruClient.first(result)` to skip the indexing.

`tarball_b64` (the default) also includes the Markdown inside the gzipped tarball, as `markdown.md` — extract the tarball and it is there too. Use `inline` when you want to read the markdown directly without unpacking; use `tarball_b64` (or `s3`) when you also want the structured JSON / image files together.

## Success response

```json
{
  "ok": true,
  "elapsed_seconds": 18.4,
  "mineru_version": "4.0.12",
  "tier": "advanced",
  "ocr_mode": "ocr",
  "image_analysis": true,
  "results": [
    {
      "basename": "doc",
      "source": "url:https://example.com/report.pdf",
      "pages_requested": 100,
      "tarball_b64": "<base64-encoded gzipped tarball>"
    }
  ],
  "debug": {"...": "..."}
}
```

### Top-level keys (job-scoped)

| Field | Type | Notes |
|---|---|---|
| `ok` | bool | Always `true` on success |
| `elapsed_seconds` | float | Wall time inside the handler. Does not include cold-start time or transport |
| `mineru_version` | string | The MinerU version that is installed in the worker and produced the parse (e.g. `4.0.12`). Never `unknown` on a worker that runs |
| `tier` | string \| null | The tier MinerU noted in the result, which is the one it used: a file read whole (Office, HTML, …) says `flash` whatever was asked. `null` only if the result carries no note |
| `ocr_mode` | string \| null | The OCR mode MinerU noted: `txt` or `ocr`, never `auto` — `auto` is resolved to what MinerU chose for the file |
| `image_analysis` | bool \| null | Whether image analysis acted: `false` outside tier `advanced` even when asked for |
| `results` | array | One entry per parsed file. Single-file jobs have a one-element list. See below for the entry shape. |
| `debug` | object | Observability data: `tier`, GPU info, phase timings, and a best-effort cached model path. See below. |
| `refresh_worker` | bool | Present only when a `REFRESH_WORKER_AFTER_*` threshold has tripped. Tells RunPod to recycle the worker after returning. |

### Per-entry keys (file-scoped, inside `results[]`)

| Field | Type | Notes |
|---|---|---|
| `basename` | string | Echo of the input `basename`, handy for correlating many concurrent jobs |
| `source` | string | Echo of the input source: `url:...`, `b64`, or `volume:/path/...` |
| `pages_requested` | int | The slice the caller asked for. `-1` if `end_page` was open-ended |
| `tarball_b64` | string | Present when `transport: "tarball_b64"`. Base64-encoded archive of the output directory — `.tar.gz` by default, `.zip` when `archive_format: "zip"` |
| `markdown`, `markdown_full`, `middle_json`, `structured_content`, `model_output`, `images` | various | Present when `transport: "inline"`. The set of keys reflects the `formats` filter — see below |
| `tarball_url`, `tarball_url_expires_in`, `bucket_key`, `bucket_bytes` | various | Present when `transport: "s3"`. The archive is `.tar.gz` by default, `.zip` when `archive_format: "zip"`. See [Output modes → s3](/guides/output-modes/) |
| `degraded` | object | **Present only when the response is short of something.** See [Incomplete responses](#incomplete-responses) |

Each job parses one file. To process many documents, submit them as individual jobs and raise `workers_max` — RunPod's queue runs them in parallel across workers (see [Scaling](/guides/scaling/)).

### When `transport: "inline"`

Each entry contains the requested format keys directly. MinerU 4 writes these files with `ParseResult.save`; `tarball_b64` and `s3` ship all of them in the archive under these names, and `inline` returns them under the keys below. The worker adds one, `markdown_full.md`.

| Key (`formats`) | File in the archive | Type | Notes |
|---|---|---|---|
| `markdown` | `markdown.md` | string | The Markdown rendering of the document. The one required artifact: a job that cannot produce it fails |
| `markdown_full` | `markdown_full.md` | string | The same document rendered by MinerU in full mode (`RenderMode.FULL`), rendered by the worker from the saved middle JSON. The default Markdown leaves out headers, footers, page numbers, margin text and page footnotes; this one is meant to keep them. Which of those classes it carries on a given document is still to be confirmed on recorded responses |
| `middle_json` | `middle_json.json` | object | MinerU's intermediate representation (`docvortex.middle`, schema 2.0): pages with ordered blocks. `extensions.mineru` records the `tier` and `parse_mode` actually used. Page indices (`page_idx`) are zero-based and refer to the original document |
| `structured_content` | `structured_content.json` | object | A consumer-facing rendering of the same pages: blocks with their text as plain strings |
| `model_output` | `model_output.json` | object | MinerU's raw model output. Absent when MinerU has none to keep, in which case the inline key is `{}` |
| `images` | `images/…` | object | `{filename: base64-encoded-bytes}` for each extracted image. Names follow `page_{page_idx}_{parent_type}_{parent_index}.{ext}`, where `page_idx` is the page index in the document the job read. A job that read a page window of one file (`start_page`/`end_page`) keeps that file's own indices, so windows of one document do not reuse names. Separate files cut from one document by the caller each start at page `0` and do reuse them |

MinerU's files are MinerU output, not a schema owned by this wrapper; treat unknown block types and extra fields as forward-compatible data rather than rejecting the response. The MinerU 3.4 files (`{basename}.md`, `{basename}_content_list.json`, `{basename}_middle.json`) and their keys `content_list` and `middle` no longer exist.

### Filtering with `formats`

The `formats` field whitelists which artifacts the inline payload contains. Omitted keys are absent from the entry — not present-as-empty. Useful when only the markdown matters and the per-page images would otherwise bloat the response.

```json
{
  "input": {
    "file_url": "https://example.com/report.pdf",
    "transport": "inline",
    "formats": ["markdown", "structured_content"]
  }
}
```

The resulting entry has `markdown` and `structured_content` only; the other keys are not present in the response. Empty list is rejected (`formats: []` is a validation error).

For `transport: "tarball_b64"` and `transport: "s3"`, `formats` is a no-op: the archive always carries every file (filtering inside an archive would be confusing for downstream callers).

### Incomplete responses

A parse can produce a file that cannot then be read — bytes that are not the UTF-8 the artifact is declared as, JSON truncated by a disk that filled mid-write, an image the filesystem will no longer describe. One corrupt file does not fail the job: the artifact comes back as its empty default, or the archive ships without that member, and the entry gains a `degraded` object saying so.

The worker adds one file of its own, `markdown_full.md`. When it cannot be rendered or written, the job still succeeds: the file is left out (inline, `markdown_full` is `""`, or absent when `formats` leaves it out; it is absent from the archive) and `degraded` names it with `reason: "unreadable"`. That is reported even when `formats` did not ask for `markdown_full`.

```json
{
  "basename": "doc",
  "source": "url:https://example.com/report.pdf",
  "markdown": "# The document's real text\n",
  "structured_content": {},
  "degraded": {
    "count": 1,
    "items": [
      {"artifact": "structured_content", "file": "structured_content.json",
       "reason": "unreadable", "error_type": "JSONDecodeError"}
    ]
  }
}
```

| Field | Type | Notes |
|---|---|---|
| `count` | int | Everything lost. `items` stops at 50, so `count` above `items.length` means the list is abridged |
| `items[].artifact` | string \| null | Which response key it cost. `null` for an archive member, which is not one of the formats |
| `items[].file` | string | Filename only — the output directory is a temp path inside the worker |
| `items[].reason` | string | `unreadable`, `unresolvable`, `outside_output_dir`, or `unsafe_name` |
| `items[].error_type` | string | Exception class name, when an exception revealed the problem |

**`degraded` is absent on an intact job**, so its presence is the signal. Treat an entry that has it as a document to reprocess: `ok` is `true` and nothing else will flag it, because from the outside an empty `structured_content` looks the same as a document that had nothing to report.

`markdown` is the exception. It is the document, so a job that cannot produce readable Markdown fails with `ok: false` rather than returning an empty string — a failed job can be retried, a successful one that quietly returned nothing cannot. The other artifacts degrade.

Every item is also emitted as a `response degraded` warning on stdout, carrying the same fields plus the `job_id`, and counted as `mineru.degraded.total` when [OpenTelemetry](/guides/observability/) is configured. The field is the per-document signal — the only thing that says *which* document to reprocess. The log line and the counter are the fleet-wide ones, and they are what tells you the rate is non-zero at all.

### Debug observability

Every response includes a top-level `debug` block with information that lets you correlate a parse to its environment without having to read worker logs:

```json
{
  "debug": {
    "tier": "advanced",
    "model_dir": null,
    "gpu": {
      "available": true,
      "name": "NVIDIA RTX 4090",
      "compute_capability": "8.9",
      "total_memory_gb": 23.99
    },
    "phase_ms": {
      "fetch_input": 12,
      "mineru_parse": 18420,
      "package": 95
    }
  }
}
```

| Field | Notes |
|---|---|
| `tier` | The tier that was asked for. Echoes the input or the default; the tier MinerU used is the top-level `tier` |
| `model_dir` | Best-effort path to a Hugging Face cache snapshot of a MinerU model. MinerU 4 keeps its baked models in its own directory (`$MINERU_HOME/models`), not in that cache, so this is `null` on a normal worker. A `probe: true` job does not list that directory either; it echoes `MINERU_HOME`, `MINERU_MODEL_SOURCE` and the engine settings, which say where MinerU looks. |
| `gpu` | Card name, `compute_capability` (8.6 = Ampere, 8.9 = Ada, 9.0 = Hopper, 12.0 = Blackwell), VRAM. Helps debug "why did my job land on a different card than my pool config?" |
| `phase_ms` | Per-phase timings: `fetch_input` (download/decode), `mineru_parse` (MinerU's `parse_async` and the save), `package` (tarball or inline assembly) |

On failure, `debug` still contains `gpu`, `model_dir`, and whatever `phase_ms` was collected before the error.

## Failure response

When the handler raises or returns an error, the response sets `ok: false` and includes a top-level `error` key. RunPod marks the job FAILED in the dashboard based on the presence of that key. **There is no `results` list on a failure response.**

```json
{
  "error": "ValueError: must provide exactly one of file_url / file_b64 / volume_path",
  "ok": false,
  "elapsed_seconds": 0.1,
  "mineru_version": "4.0.12",
  "traceback": "Traceback (most recent call last):\n  File ...",
  "debug": {"gpu": {"...": "..."}, "model_dir": "...", "phase_ms": {"...": "..."}}
}
```

| Field | Type | Notes |
|---|---|---|
| `error` | string | Type name + message, e.g. `ValueError: ...` |
| `ok` | bool | Always `false` on failure |
| `elapsed_seconds` | float | Time before the error |
| `mineru_version` | string | Version that was running |
| `tier`, `ocr_mode`, `image_analysis` | string \| null, string \| null, bool \| null | How the document was read, as in the success response. Present only when the parse had finished before the failure (a response too large to deliver, an upload that failed); a job that failed earlier carries none of them |
| `traceback` | string | Last 5 frames of the Python traceback; useful for debugging |
| `debug` | object | Same shape as the success response — `gpu`, `model_dir`, and whatever `phase_ms` was collected before the failure |

`error` and `traceback` are normalized before they are returned: URLs inside them keep their scheme, host and path but drop credentials, query and fragment, and very long text is truncated. The same text goes to the worker's logs and, when [OpenTelemetry export](/guides/observability/) is configured, to the collector — so one failure reads the same in all three places.

## Progress updates (streaming)

The handler posts `{"status": "IN_PROGRESS", "output": ...}` events during a parse, which is what `/status` and `/stream` report while the job runs. Phases:

```json
{"phase": "fetching_input"}
{"phase": "parsing", "input_bytes": 1234567, "input_format": "pdf", "start_page": 0, "end_page": 99}
```

Each update is **awaited before the parse continues**, rather than posted from a background thread the handler does not wait for. Progress travels to the same job-results endpoint as the final result, so an update still in flight at completion can be applied after the `COMPLETED` status and leave a finished job stuck `IN_PROGRESS`. Waiting for it is what keeps the two in order regardless of how fast the parse is — whole-document inputs (Office, HTML, …) skip model inference and can finish in under 100 ms.

There is deliberately no `packaging` phase event either: it would carry no information a caller can act on, and no update is emitted after the parse.

With the RunPod SDK, submit asynchronously and stream from the returned job:

```python
job = endpoint.run({"file_url": "https://example.com/report.pdf"})
for update in job.stream():
    print(update)
```

The HTTP equivalent is `GET /v2/{endpoint_id}/stream/{job_id}`. The
`MineruClient` wrapper only supports `run_sync`, so use the RunPod SDK or HTTP
directly when you need progress.

## Validation behaviour

The handler validates input before doing any work:

1. **Field types and bounds** via `runpod.serverless.utils.rp_validator`. Wrong type, missing required field, out-of-range value, or unknown field name raises `ValueError`.
2. **XOR source rule.** Exactly one of `file_url`, `file_b64`, `volume_path` must be set. Zero or two raises `ValueError`.
3. **Basename safety.** Every character in `basename` must be alphanumeric, `-`, or `_`, and the whole label at most 128 characters. Unicode letters and digits are accepted.
4. **Inline file size.** The worker rejects decoded `file_b64` data over 20 MB — measured first on the encoded string, then on the decoded bytes. RunPod's whole-request limits are reached earlier because base64 expands the raw file; use the practical thresholds above.
5. **File type.** MinerU decides from the bytes whether it reads the file; a file it does not recognise fails the job with the detected type (or says it found none), and one it recognises but cannot read fails it with MinerU's own reason. The worker does not pre-check magic numbers.
6. **`formats` membership.** Each entry must be one of `["markdown", "markdown_full", "middle_json", "structured_content", "model_output", "images"]`; empty list is rejected; duplicates are silently collapsed.
7. **URL fields.** `file_url` must be `http(s)` with a host and resolve to a publicly routable address unless `MINERU_ALLOW_LOCAL_FETCH=1`. See [URL inputs](#url-inputs).
8. **`volume_path` roots.** The path must be absolute and, once resolved, sit under one of the worker's input roots. See [What `volume_path` accepts](/guides/network-volumes/#what-volume_path-accepts).
9. **Reading settings.** `tier` must be one of `flash`, `basic`, `standard`, `advanced`; `ocr_mode` one of `auto`, `txt`, `ocr`. The fields MinerU 4 removed (`backend`, `effort`, `lang`, `formula_enable`, `table_enable`, `server_url`) are rejected with what replaces them.
10. **Page range.** `start_page` must be `>= 0`; an `end_page` of `0` or more must be `>= start_page`. If the endpoint sets `MINERU_MAX_PAGES_PER_JOB`, an explicit range larger than that is rejected — see [Scaling](/guides/scaling/). A PDF window that selects no page of the document (a `start_page` at or past its page count) fails the job naming `start_page` and `end_page`, followed by MinerU's own reason, which speaks of its 1-based `page_range`.

All validation errors produce a failure response with `error: "ValueError: ..."` and the job is marked FAILED.

## Source of truth

This page is regenerated by hand when the contract changes. The authoritative source is the docstring at the top of [`handler.py`](https://github.com/sergeyshmakov/mineru-runpod/blob/main/handler.py) plus the `INPUT_SCHEMA` dict and `validate_input` function in [`worker/schema.py`](https://github.com/sergeyshmakov/mineru-runpod/blob/main/worker/schema.py). If you see a discrepancy, the code wins; please open an issue so the docs page can be updated.

The `formats` values and the `transport` list are not spelled out in the schema: the formats are the keys of the output manifest in [`worker/harness.py`](https://github.com/sergeyshmakov/mineru-runpod/blob/main/worker/harness.py), in declaration order, and the transports are whatever the [`runpod-doc-worker`](https://rdw.shmakov.tools) harness can pack. Response assembly — the `results` entries, the archive, the presigned URL — is that harness's; which files go into it is the manifest's.

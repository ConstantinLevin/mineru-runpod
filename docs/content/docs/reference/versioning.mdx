The version on this repo describes a **deployment template**, not a library on a
package index. That shapes the whole scheme, so it is worth stating plainly.

## What moves each part

| Part | Moves when |
|---|---|
| **Major** | MinerU itself has a major release |
| **Minor** | New features, and breaking changes shipped under the two headings below |
| **Patch** | Fixes and internal work |

The major is reserved for the engine because that is the change which actually
moves output quality and behaviour. Nothing else takes a major, so the number
never drifts out of step with the engine it names.

## Two kinds of breaking change ride a minor

Both get their own section at the **top** of the release notes, above Features.
If you read nothing else before upgrading a minor, read those.

| Section | Covers |
|---|---|
| **Job Contract Changes** | A renamed job field, a default that flips, a value that used to be accepted and now is not |
| **Compatibility Changes** | A raised Python floor, a dropped interpreter, a removed import path |

### Why not a major

`mineru-client` is not on PyPI. It installs from a git URL:

```bash
pip install "mineru-client @ git+https://github.com/sergeyshmakov/mineru-runpod"
```

Nothing you can write there range-pins a version, and no resolver ever reads one.
A major bump therefore cannot warn you any better than a release note can — while
spending the major on it would leave the number one behind the MinerU major it
is reserved for, and further behind after every such change. The release notes are
the channel that reaches you; the digit is not.

That also means the practical advice is the same either way: **pin a tag** if you
need stability, and read the notes when you move it.

## Engine compatibility

| | |
|---|---|
| **MinerU series** | `4.0.x` |
| **Pinned as** | `mineru[torch]==4.0.12`, with `mineru-vl-utils==2.0.7`, `docvortex==0.5.16` and `runpod==1.10.0` |

The engine version is stated here, in the README, and in the Hub listing, rather
than encoded in the template's version number — "v4.0.0" would not tell you which
MinerU you are getting. The pin is minor-locked, so an engine major cannot arrive
by accident.

## Upgrading from 1.x

2.0.0 is the first release on MinerU 4. The last 1.x release, 1.13.0, ran MinerU
3.4. The engine major changes two things for you.

**Callers** send a new job contract. `tier`, `ocr_mode` and `image_analysis`
replace `backend`, `effort`, `lang`, `formula_enable`, `table_enable` and
`server_url`, and a job that still sends one of the old fields is rejected with
what takes its place. See [API reference → Fields MinerU 4 removed](/reference/api/#fields-mineru-4-removed).

**Operators** check the endpoint's environment and any build arguments against the
tables below. A variable that was removed is ignored, not rejected, so a setting
left over from 1.x does nothing and says nothing.

### Runtime settings (Hub template and endpoint environment)

| In 1.x | In 2.x |
|---|---|
| `MINERU_WARMUP_BACKEND` (default `vlm-auto-engine`) | `MINERU_WARMUP_TIER` (default `advanced`) |
| `MINERU_WARMUP_LANG` | removed; MinerU 4 has no `lang`. New: `MINERU_WARMUP_OCR_MODE` (default `ocr`) sets how the warm-up reads |
| `MINERU_VL_MODEL_NAME` | removed; it chose the VLM of the `*-http-client` backends. The image bakes one pinned VLM |
| `MINERU_HYBRID_BATCH_RATIO` | removed (a MinerU 3.4 knob). Nearest: the new optional `MINERU_VIRTUAL_VRAM_SIZE`, which moves vLLM's GPU memory share and MinerU's batch sizes |
| `MINERU_ENFORCE_TARGET_POLICY`, `MINERU_ALLOWED_SERVER_HOSTS` | removed together with the job field `server_url`, which they governed; nothing replaces them |
| `MINERU_MODEL_SOURCE` (Hub setting) | no longer offered; the image fixes it at `local`, because the models are baked in and loaded offline |
| `HF_TOKEN` (Hub setting) | no longer offered; the worker downloads nothing at runtime |

### Build arguments (Dockerfile)

| In 1.x | In 2.x |
|---|---|
| `VLLM_VERSION` | `VLLM_IMAGE`, the full base image reference pinned by digest |
| (none) | `MINERU_SMALL_MODELS_REVISION`, `MINERU_VLM_REVISION`: the pinned commits of the baked model repositories, checked at build time |

### Set by the image, not by you

`MINERU_HOME`, `MINERU_MODEL_SMALL_BACKEND`, `MINERU_MODEL_VLM_ENGINE`, and the two
`MINERU_LLM_AIDED_FEATURES_*` switches, which are off. They are not operator
settings; the image sets them so that MinerU finds its baked models and never
calls a service outside the container.

An endpoint variable of the same name overrides the image's value. That includes
`MINERU_MODEL_SOURCE`: if a 1.x endpoint set it, remove it, or MinerU no longer
loads only the baked models.

## Reading the notes

Releases are cut by semantic-release from the commit history, and the sections
above come from commit types (`contract:` and `compat:`) rather than from anyone
remembering to write them. That mapping is asserted in CI, because a policy which
depends on configuration nobody checks stops applying quietly.
